# IssueOps ten-stage skills, CLI-owned stage detection, and the auto execution mode

- Date: 2026-09-05
- Kind: `adr`
- Source: issueops ten-stage refactor (.agent-harness/plans/issueops-ten-stage-refactor.md)
- Summary: IssueOps now presents ten user-facing stages with one owning skill each, stage detection moves from model memory into `agent-harness issueops next`, planning happens before worktree provisioning, and `execution prepare --mode auto` picks Orca when it is ready and direct when it is not. Repeated procedures move into three shared skills (`issueops-review`, `gates-ledger`, `issueops-remote-write`), and leaving a cycle from any stage becomes a first-class path (`issueops-abandon`, with remote effects opted into on `cleanup abandon`).
- Context: The harness exists so the same procedure runs on Codex, Claude Code, and Omo, and so a team-shared issue stays the single source of truth for the contract and the progress. Neither held. Each stage skill re-derived the current phase from the record in its own way, so two agents could disagree about where a cycle stood; the same procedures (adversarial review, gate ledgers, the remote write protocol) were copied into several skills, so one copy would get fixed and the others would rot; an unmerged cycle had no exit at all, because `remote close-issue` and `cleanup remote-branch` both hard-gate on merge evidence and `cleanup abandon --apply` deletes the record that every `--id` command needs. A spike on 2026-09-05 also measured that `link-issue` auto-advances the phase to `plan` when plan readiness is satisfied, which means phase alone cannot tell a freshly created cycle from a planned one.
- Decision: (1) Ten stages, one skill each: confirm/create the issue, prepare the branch, read docs + plan + review + hand off, implement, AI-slop clean, reflect project docs, verify, commit/push, publish/complete, post-merge cleanup. (2) `agent-harness issueops next` is a read-only command that classifies the stage from the record plus local observation — no fetch, no provider call, no Orca RPC — and returns the stage key, the missing gates, the next command, and the exits. Go returns keys and commands; the router skill owns the table that turns a key into a skill name and a Korean label, so renaming a skill never regenerates a golden. (3) Stage 2 records branch identity only. `execution prepare` is the single owner of worktree provisioning in both modes, because Orca creates its own branch and worktree and a pre-created one collides. (4) Planning therefore runs before provisioning, and the handoff is `execution prepare --mode auto`: the probe decides, the skill does not. Orca launches the implementation session and leaves the lease claimable; direct keeps the current session as generation 1. (5) Repeated procedures get one owner each: `issueops-review` (adversarial review and the revise/stop loop), `gates-ledger` (gate ledgers), `issueops-remote-write` (the remote write protocol and the Korean artifact gate). (6) `issueops-abandon` owns pause and abandon; `cleanup abandon` grows `--close-pr`, `--close-issue`, and `--delete-remote-branch`, applied before the record is deleted because no `--id` command works afterwards. Resume and takeover stay with the `next_command` chain the router documents.
- Consequences: This supersedes the "main session plans only" clause of the [2026-07-24 planner/implementer dual structure](decisions/2026-07-24-issueops-planner-implementer-dual-structure.md). The dual structure itself stands: a planner session still prepares, and an implementer session still holds the lease. What changed is where the boundary sits (after planning, not before) and who decides the mode (the probe, not the skill). `issueops-branch-worktree` is deleted, and four `skills/issueops/references/*.md` files are deleted with their live rules moved to the owner that uses them. The record schema is unchanged at `schema_version: 1`; `issueops next` adds no field and writes nothing. `IssueOpsStrictPRReadiness` splits so that a local, fetch-free readiness surface exists for stage classification. Cycles in flight keep working: `next` classifies them from the artifacts they already have. Follow-up: reflecting stage transitions into the issue body's managed block (a `remote reflect-stage` surface) is not part of this decision.

- Alternatives / rejected options:
  - Add a `handoff` execution mode alongside direct and orca — rejected: the difference between the two paths is one command (claim), not a third state machine, and a third mode would need its own preflight, recovery chain, and golden surface.
  - Let the execution owner write the plan — rejected: Orca preflight requires planner-owned records the owner cannot supply, so the owner would have to fail and hand back, which is the loop this refactor removes.
  - Make release + reseed the normal way to move a cycle between sessions — rejected: reseed exists to recover a completed execution, and normalizing it would blur the audit trail between recovery and routine handoff.
  - Let a SessionStart hook announce the current stage — rejected: hooks are context-only by the 2026-08-27 decision, and a hook that reads IssueOps state would put stage detection back in two places.
